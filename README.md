# AI 研发工作区使用指南

这套框架保存算法的来龙去脉：设计文档解释“应该怎样”，代码说明“实际怎样”，Run 记录“某次分析发生了什么”。AI 根据问题选择这些材料，核对版本与差异，再把新的结果和经验写回。

**你不需要预先整理成项目，也不需要手动填写全部模板。** 给出问题、材料路径和允许处理范围即可。核心算法、Run、Research 和工具都是平级对象；项目只是可选的交付视图。

## 从这里开始

已有旧的完整工作区副本：可以直接把其中的运行环境补到 GitHub 新版，通常无需重新下载。按 [复用旧副本运行环境](docs/WINDOWS_PORTABILITY.md#用旧完整副本补齐-github-新版) 复制目录、自检并重建索引。

GitHub 仓库保存框架源码、规则、模板和测试，不包含本机 Python、模型、依赖缓存、查询历史或离线 ZIP。克隆源码后，先用已有 Python 和 pip 执行 `python services/qdrant/install.py --apply`，再用生成的 `services/qdrant/runtime/python.exe services/qdrant/download_model.py --apply` 下载公开模型；这些首次安装步骤需要联网。完成后运行 `portable.cmd check`，正常检索使用本地模型。完整离线迁移包与 GitHub 源码版的区别见 [迁移指南](docs/WINDOWS_PORTABILITY.md)。

Windows 之间迁移：运行 `portable.cmd pack --apply` 生成包含 Python、模型和依赖的完整离线包；接收端解压后双击 `portable.cmd` 自检。操作与边界见 [Windows 迁移指南](docs/WINDOWS_PORTABILITY.md)。

第一次导入：

> 整理这批材料【路径】，用于【问题/算法】。原件保留原位，分批阅读，建立核心算法、关键词和文档—代码关系。列出未读、冲突和提取失败项，保存进度后更新索引。

日常问答：

> 关于【算法】的【问题】，先读取算法说明，再按需要检查实现和历史结果。如果证据不够，逐级扩展上下文，直到找到依据或明确缺少什么。

控制读取范围：

> 这次必须看【文件 A】，完整读取【文件 B】，不要加入【文件 C】。这些选择在本次排查中保持；如果要长期使用，我会明确说“以后也这样”。

常用技能已安装到本工作区 `.agents/skills/`：

| 调用 | 用途 |
|---|---|
| `$workspace-context` | 算法问答、文档与实现核对、证据不足时扩展上下文 |
| `$context-maintenance` | 整理、批量导入、版本变化与映射维护、保存续作进度 |

新安装的技能可能需要重新打开会话才能被客户端发现。当前会话也可直接说“读取 automation/workflows/workspace-context/SKILL.md 后处理这个问题”。其他研究、诊断和报告方法按需读取 [工作流目录](automation/workflows/README.md)，不必记很多技能名。

## 主要概念与文件夹

| 概念 / 位置 | 是什么、放什么 | 怎样维护 |
|---|---|---|
| 核心算法（测校项） `core-algorithms/<slug>/` | 公司算法/模块文档定义的关键模型算法。module.json 登记文档来源、ID、别名和关联；README 说明工程目标、模型、边界及子系统协同 | 先核对文档定义，再建卡；仅核心实现放 code/。普通函数、辅助脚本和编排功能归 tools/automation/runs，算法间通过 MOD-ID 关联 |
| Run `runs/<run-id>/` | 一次有独立输入和结果的分析/仿真/验证。run.json 保存版本、配置、结论、限制、产物和复核状态 | AI 分析后写回；新版本分析建新 Run，纠错追加历史。可同时引用多个核心算法和研究 |
| Research `research/<topic>/` | 围绕一个问题的探索过程：计划、论文/材料、证据台账、反证和综合 | AI 按问题推进；实验结果引用 Run，成熟结论再晋升到核心算法或知识 |
| 知识 `knowledge/` | 可复用经验、重要决策 ADR、事故复盘。强调结论的依据、适用范围和限制 | AI 按 MEMORY 复核后整理；有新反证则质疑/撤回/替代，保留旧记录 |
| 项目 `projects/<slug>/` | 可选的目标、里程碑和交付聚合，引用已有核心算法/研究/Run | 需要追踪交付时创建，不复制算法或按项目分割公司知识 |
| 工具 `tools/` | 可复用脚本、代码包和适配器；registry.json 登记入口 | AI 复用/开发时补接口、用途和适当验证；应用界面不自动当成核心算法 |
| 数据 `data/` | catalog 数据卡说明数据在哪里，contracts 定义字段/单位，lineage 记录流转 | 用户提供含义与范围，AI 登记版本与检查；原始大数据保留获批存储 |
| 报告 `reports/` | briefs 需求、sources 源文件、templates 模板、manifests 证据映射、generated 生成件 | AI 按任务制作，正式数字引用固定 Run；上游变化需复查 |
| 检索 `retrieval/` | 来源登记、检索/上下文配置、评估集、调查与反馈；generated 是可重建缓存 | 写回材料后更新索引；查询也自动刷新；真实反馈用于改来源、别名和阅读策略 |
| 本地运行时 `services/qdrant/` | 便携 Python、Qdrant local、多语言嵌入模型、OCR、数据库与离线安装包 | 框架维护时升级；正常推理离线，模型文件校验后加载 |
| 导航 `context/` | START_HERE 入口、NOW 现状、MEMORY 记录规则、交接、派生索引 | AI 在重点变化/交接时更新，不堆聊天全文 |
| 自动化 `automation/` | CLI、测试、工作流源；`.agents/skills/` 只放技能发现入口 | 实现或用法变化时更新；方法正文只维护一份 |
| 待办/归档 `inbox/`、`archive/` | 尚未整理的小材料或路径清单 / 冷存档 | AI 按用户范围处理，默认不检索、不自动搬移或删除 |
| 规则/手册 `governance/`、`docs/` | 数据边界与保留策略 / 操作指南、模板和历史设计 | 根规则优先，当前手册随实现更新，历史设计保留日期和背景 |

`slug` 是目录短名；MOD、RUN、RES 等 ID 是稳定身份，不应随文件位置随意变化。`_template/` 是创建模板，不是事实。核心算法卡可只写当前需要的内容；详细公式/接口模板在 docs/templates，避免重复维护两份算法正文。

**Research 保存探索，Run 保存一次实验，Knowledge 保存可复用结论，Project 保存交付安排。** 它们通过引用连接，不需要相互包含。同一结论保留一个主要正文，其他位置放链接。

## AI 会把哪些材料加入上下文

检索命中只是候选，不等于全部阅读全文。当前使用三个阶段：

| 阶段 | 默认怎么读 | 什么时候继续 |
|---|---|---|
| focus：聚焦 | 目标核心算法算法说明优先全文；少量核心代码和相关证据；应用文件/项目安排通常需正文命中才加入 | 缺定义/调用方、证据无法支持答案、文档与实现冲突 |
| investigate：核对 | 增加候选数量和片段长度，补相关 Run、代码、研究、知识；可定向指定文件或细化问题 | 仍有证据缺口或需跨核心算法反证 |
| wide：扩大 | 放开核心算法/项目过滤，在已获准索引里扩大搜索，并扩展两跳关联 | 到此停止自动扩大，说明具体缺口；新的范围/预算由明确任务决定 |

- **算法说明是阅读基线**，不会因只有向量命中就默认只给片段。用户明确排除、缺失或预算不足时，清单会指出，AI 不得假装已读全。
- 核心代码短则全文、长则片段；Python 能定位且容纳时读取完整命中函数。应用代码和展示层可用角色标记排除。
- 短 Run 可全文；长 run.json 首轮摘录问题、结论、版本/输入、复核和限制等字段。长日志与其他材料先取片段，证据不足再展开。
- Research、Knowledge 和 Project 也按相关性、角色、长度与预算加入；目录名本身不保证有用或可信。
- PPT/PDF/图片/表格默认定位片段和资产路径；OCR 不能代替图表/公式理解。

每份证据包都附候选清单：来源、角色、原文长度、选入原因、full/brief/excerpt/omitted、排除/延后原因、版本及风险。CLI 只生成包，AI 需要继续读取包与清单。

**“自动扩大”由当前任务中的 AI 根据证据缺口触发，不是程序能自动判断任何回答的正确性。** AI 调用反馈命令后，程序自动生成下一阶段；最多扩展两次，不自动增加字符预算，也不解除用户排除项。已经加载到聊天里的旧内容无法由 CLI 撤回，后续应优先补新增证据，避免重复塞入全文。

## 你可以怎样干预和改进

| 直接告诉 AI | 对应行为 |
|---|---|
| “这份必须看 / 这份完整看 / 这份别看” | 本次 --include / --full / --exclude，并在调查链中保留 |
| “还是没解决，缺少调用方” | 记录 unresolved，定向补充来源或细化问题后进入下一阶段 |
| “文档和实现的假设不同” | 记录 conflict，保留两方依据，检查版本和实现；不默认任何一方正确 |
| “这个问题已解决，这份证据最有用” | 记录解决反馈和单份来源反馈；不自动把 Run 改为已复核 |
| “以后这个核心算法都排除应用代码” | AI 更新持久偏好，保留配置变更记录；当前明确选择仍可覆盖 |

持久偏好在 retrieval/context-policy.json；文件角色、关键词和关联在 retrieval/sources.json。反馈不直接训练模型或修改权重，也不把一次成功变成永久规则。改策略后用真实标注问题检验，有需要再保留改善。细节见 [上下文与检索手册](docs/RETRIEVAL.md)。

## 导入和更新已有知识

1. 给出材料路径、用途和范围，AI 建有界清单；外部文件逐个登记，不扫描整块共享盘。
2. 分批阅读，记录已读/部分/未读、关键词、算法与代码版本、章节/函数和来源角色。
3. 融合到已有核心算法/研究；副本用主引用，修订版记版本链，冲突保留两方证据。导入成功不等于算法已验证。
4. 保存后运行 index-knowledge，再用几个真实问题检查召回和上下文选择；未支持格式/抽取失败留在清单。
5. 文档、函数、参数或映射变化时直接告诉 AI；复杂变更用维护技能。比较前后版本，更新关系、检查受影响证据，保留旧 Run。

完整示例与批次清单见 [材料导入与变更](docs/EXISTING_MATERIALS.md)。

不常用命令无需记忆，让 AI 执行即可：

```powershell
.\automation\workspace.ps1 new-core-algorithm alignment --title "时间对齐" --source-document "公司测校项文档名称或编号（示例）"
.\automation\workspace.ps1 new-run --title "低采样率验证" --module MOD-ALIGNMENT
.\automation\workspace.ps1 index-knowledge --dry-run
.\automation\workspace.ps1 refresh-index
.\automation\workspace.ps1 validate
```

## 附录：检索和向量化到底怎样工作

### 全文搜索是在暴力搜根目录吗

**查询使用 SQLite FTS5 倒排索引，不是每次用字符串匹配暴力扫描全根目录。** 系统将提取正文分词，把“词项出现在哪些片段”预先记入数据库；查询从词项找到片段，结合覆盖率、BM25 和原句命中排序。

另一个步骤是“索引刷新”：目前每次查询前会枚举 retrieval/config.json 指定的业务目录和显式来源，读取文件计算 SHA-256，确认哪些变化了。这里确实有受限目录遍历和文件哈希开销；模板、运行时、模型、generated、归档等默认跳过，不扫描未登记的外部目录。原文抽取和向量化只重做变化项，但当前仍需为获准文件计算哈希。材料很多时，这一步可能成为瓶颈，尚无后台文件监听。

### 每份材料会自动提取关键词吗

有两个不同过程：

- **机械分词**：CLI 自动做中文双字滑窗，英文/代码标识符拆词，用于全文索引。这不是语义摘要，也不是人工整理的关键词。
- **业务关键词**：AI 在实际阅读/整理时写入核心算法 aliases、Run keywords 或 sources 的 keywords；普通手动存文件不会自动调用大模型提词。它们进入 FTS 的加权标题字段，也随标题作为限长前缀参与嵌入。查询别名表 aliases 还能扩展同义词。

研究笔记或历史材料没有结构化关键词时，正文仍可被全文与向量检索。不要把“已分词/已建索引”当成“AI 已读懂、已整理完”。

### 各种材料怎样向量化

正文/代码、Run 字段以及 PPT/PDF/OCR/表格的提取文本，先切成可定位片段；再按模型 tokenizer 分窗：正文最多 360 token、步长 300，标题与关键词前缀最多 40 token。成熟的本地多语言 MiniLM 将每窗编码成 384 维向量，Qdrant local 保存向量及来源 ID、指纹、模型身份、片段位置和核心算法信息。

问题用同一个模型编码后，与保存的向量计算余弦相似度。**图片本身没有做视觉向量化**；当前编码的是 OCR、替代文字和相关页文字。Qdrant 不负责训练模型，本地嵌入模型也不会因日常使用自行更新权重。

当前安装的是 Python Qdrant **local 模式**：实现对本地向量计算相似度，不能把它等同于服务器模式的 HNSW 大规模近似检索。适合先跑通单用户闭环；语料扩大后需实测性能，再考虑同机服务模式。

两路候选按文件去重并用排名融合：

$$
S(d)=\sum_{j\in\{\mathrm{FTS},\mathrm{vector}\}} \frac{1}{60+r_j(d)}.
$$

其中 $d$ 是来源文件，$r_j(d)$ 是它在第 $j$ 路的文件排名；没有命中该路则不加分。相关性分数只帮助挑选证据，不代表结论可信。随后，独立的上下文机制按算法基线、角色、用户选择和预算决定实际读多少。

### AI 存档时会先向量化再保存吗

**不会。原文件先保存，检索库随后增量更新。** 维护技能要求在一批材料写回后调用 index-knowledge；search-knowledge、retrieve-context 和后续扩展查询也会自动刷新。普通编辑器保存或 AI 写文件本身没有文件系统钩子，不会立刻触发向量化；new-run 创建空记录也不代表正文已经分析或编码。

刷新时检查正文指纹、登记元数据、相关核心算法卡和抽取策略；变化项重新提取/编码并替换向量，缺失/禁用项停止召回。装载前再次核对来源。旧查询和反馈保留；索引中的历史指纹不替代旧原文备份。
