# 核心算法规则

## 收录边界

本目录只收录公司正式算法/模块文档定义的关键模型算法。一个对象对应一个有工程目标、模型/计算方法、输入输出和适用边界的算法项，可通过子系统协同实现；不按代码文件、类、函数或软件包的数量拆卡。

- 建卡前必须定位公司文档的名称/编号或受控路径，记录版本、章节与阅读状态；文档原名中的“模块”保留为来源名称或别名。未知版本可留空，不能编造。
- 有公司文档定义且属于关键算法才收录。仅有一个脚本、函数、通用数值方法或“模块化实现”不能作为准入依据。CLI 要求 source_document，但非空引用不证明业务资格、文档已读或模型已验证。
- 未能确定是否属于公司关键算法：记录到 inbox 的接入清单或 research 的候选研究，暂不建立核心算法对象。不为框架自带检索、索引、OCR、文件读写、流程编排或绘图功能创建算法卡。
- 通用辅助脚本放 tools/scripts，复用包放 tools/packages，工作区编排放 automation，一次性分析脚本随 runs 保存。它们可关联 MOD-ID，但关联不改变对象类别。
- code/ 只放实现本算法文档所述模型的受控核心代码；辅助代码通过路径/符号引用。一个核心实现包含多个函数时仍按文档定义的算法项归组。

目录名称为 core-algorithms；module.json、module_id、module_ids、related_module_ids、MOD-ID 和 --module 是兼容的机器标识，均仅指本节定义的核心算法，不表示通用软件模块。

核心算法独立于项目。核心算法之间以稳定 MOD-ID、接口、数据与证据关联；不因服务不同任务复制算法卡或创建相同算法的项目副本。

- 每个核心算法的 module.json 定义 ID、名称、别名、相关核心算法/研究/工具，README 保存用途、来源版本和验证依据。
- code/ 可放受控实现，外部仓库保留原位，在检索 sources 注册明确文件与 module_ids。
- 接口、单位、坐标、时间基准、公式、假设、失效边界、V&V/UQ 按实际任务补充。验证不能仅凭执行成功。
- 本算法的独立分析使用 `new-run --owner MOD-ID` 保存在本对象的 runs/；无归属轻量任务才使用根 runs/。可同时关联多个核心算法和研究，但只有一个物理归属，不复制 Run；项目仅是可选聚合，不决定核心算法或 Run 的身份。
- 公式用 LaTeX 并定义变量；代码注释说明意图、边界、单位和非显然选择。
- 变更后复查文档—代码对应与受影响依据，保留旧证据，刷新导航和检索索引。

## 核心算法工作参考（按任务选择）

1. 识别目标核心算法及上下游，不先假定局部指标代表系统目标。
2. 对齐接口：shape、dtype、单位、坐标、参考系、时间基准、频率、时延、错误语义。
3. 把算法写成“目标—方程—假设—参数来源—数值实现—适用域—失效模式”。
4. 把数据资产 ID 与核心算法 ID 双向链接。
5. 设计 Verification、Validation、UQ 和回归基准。
6. 任何影响稳定接口或技术路线的选择写入 ADR。

## 数值与控制类检查

- 明确离散时间/连续时间、采样率、滤波相位、延迟和同步策略。
- 检查量纲、缩放、坐标变换、符号约定和零点/标定版本。
- 记录边界条件、饱和、溢出、NaN/Inf、异常值、收敛与停止条件。
- 若使用随机过程，固定并记录随机种子，同时报告重复试验分布而非单次最好结果。
- 容差必须有来源：物理需求、测量不确定度、数值误差预算或历史基准。


本目录材料进入问答上下文时遵循根分阶段策略；算法必读不表示算法必然正确，Run 摘录不表示完整证据已读。新增/修改材料的整理批次结束后更新 index-knowledge。
