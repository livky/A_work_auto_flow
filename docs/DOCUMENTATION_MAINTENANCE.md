# 文档维护约定

必读路径及承载内容由 [development-checks](../automation/workflows/development-checks/SKILL.md) 定义；本页规定如何让它们保持少而准确。六份必读文档组成一个可完整读完的开发入口，不再串联全部历史。详细文档只在实际影响涉及它时展开。

## 一件事在哪里维护

| 内容 | 唯一现行位置 | 其他文档的边界 |
|---|---|---|
| 产品用途、主要概念、目录维护、导入与常用操作 | 根 README | 提供简要解释与链接，不复制长篇契约 |
| 技术栈、模块依赖、状态所有权、影响关系 | 根 ARCHITECTURE | Project 不再维护平行全局影响图；保留历史快照及本次处置 |
| 核心流程伪代码、必要解释、选项差异与实现文件索引 | docs/CORE.md | 人类易读优先；不展开字段、接口参数、算法常数或存储目录，AI 按需读代码；历史 baseline CORE 保留原义 |
| 细节入口与当前/历史分类 | docs/README.md | 必读只读索引，不自动展开全部链接 |
| 文档职责与维护边界 | 本页 | Skill 只引用规则，不再复制操作流程 |
| 测试选择及风险触发 | docs/TESTING.md | 命令、AI 场景在 TESTING_REFERENCE；定义在 catalog，结果在任务记录 |
| 选择理由、历史错误、演进与未决讨论 | docs/DEVELOPMENT_HISTORY.md | 方案讨论前读、开发后维护；详细讨论/回执仍在原设计、Project 或 Run |
| 记录语义及完整机器字段 | RESEARCH_RECORDING、运行 schema/contracts | CORE 说明 Skill 解析/写作顺序、关键文本结构及本地保存算法；完整字段仍以运行契约为准 |
| 具体功能使用、模块细节 | 索引中对应现行手册 | 修改原稳定路径，不为每版增加平行“当前手册” |
| 任务目标、决定、实际验证与延期 | 所属 Project 的计划/摘要或 Run | 不进入必读架构；旧回执和固定依据不改写 |

## 维护闭环

开发前完整阅读六份必读文档，按架构影响表定位相关细节及实际代码；已有任务计划可直接记录范围和测试选择。开发后再次完整阅读六份，逐项核对概念、功能、技术栈、模块依赖、状态归属、目录作用、用法、测试入口及索引。同步受影响细节，检查引用的契约和示例仍可执行。

每次讨论方案前另外完整阅读 [开发决策与演进记录](DEVELOPMENT_HISTORY.md)，理解原理由与教训；讨论形成实质决定或分歧时补记。每次开发后重读维护其选择、实际结果、失败及替代关系；长过程链接原记录，保持摘要简短，不把历史推翻为从未发生。

本次计划/摘要记下每份必读文档及相关细节的处置：**已修改 / 已核对无需修改 / 延期及原因**。无需为每句话生成回执，也不要求每个文件都改。关键缺口尚未处理时明确其影响，不能把“文档已写”当成“功能已实现”。

结构变化后刷新工作区索引并 validate；链接、功能说明、契约一致性与真实测试分别报告。无需变化的代码、模型和数据不因文档维护而重跑整套测试或迁移。

查询、关联、组装、记录生成、Skill 指导或保存机制变化时，同次核对 CORE 的流程、关键选项与边界，更新必要的伪代码和实现文件链接。细节变化只有影响核心理解时才展开到 CORE；完整字段、参数和算法实现留在对应手册/代码，AI 按需读取。记录实际核对日期；当前无自动文档同步服务。

## 逐项 Skill 闭环

每次开发后，以 `automation/workflows/*/SKILL.md`、安装器 `NAMES` 和 `.agents/skills/` 的并集逐条检查：触发时机是否明确，方法是否适配当前记录和权限规则，公开命令及字段是否存在，源文件、发现入口、注册和 README 链接是否一致。本次 Run/摘要为每项记录 **修改 / 已检查无需修改 / 退休及替代入口 / 延期及原因**。机械登记校验不能代替逐条阅读判断。

不再适用或重复的工作区 Skill 可以合并后删除；先保存需要保留的独特指导，检查固定引用和发行清单，登记原文指纹与去向。用户自定义入口不得按名称批量覆盖或删除，全局插件 Skill 不属于这项清理范围。新增常用 Skill 应登记发现入口并验证安装预览；只改方法正文时复用现有轻量入口。

## 控制文档增长与保留历史

- 精简前逐项核对架构原则、概念边界、状态权威、事务/恢复、权限/版本/预算、AI 与程序分工及已知实现差距。仍有效的约束必须保留在 ARCHITECTURE 并有开发入口；移动时记录去向，已被替代的定义说明替代依据，不能只删掉文字。参数细节可按需展开，稳定设计约束不能因“易读”而消失。
- CORE 精简时必须保留整体功能块的身份、定义、输入输出、职责边界、功能交接及到 ARCHITECTURE 模块影响表的映射。可压缩字段和实现参数，不能用流程伪代码替代或删除开发所需的功能分工；全局模块影响仍只在 ARCHITECTURE 维护。

- 必读文件只保留跨模块理解必需的内容。详细参数、示例、完整测试矩阵和历史执行数量移到对应细节入口；新增前先看是否可并入现有文件。
- 新增细节文档必须在 docs/README 的一类中可找到，写清承载内容和何时阅读；新的阶段计划、调查和回执放所属 Project/Run。不按每次版本复制整套 docs。
- 已有 docs 历史文件原地分类，必要时只改可变导航页提供现行入口。冻结基线、规范 commits、Run、原始材料和 fixture 不因整理而改字节或重新算哈希。
- 移动/删除旧文件前须核对固定来源、普通链接和发行清单；被固定引用的材料保留原位置或显式映射。本轮使用原地分类，不实施批量迁移。
- 当前实现以代码、schema 和适用的实际回执核对。设计目标、用户要求、功能存在与验收通过分开写；历史失败、缺失来源和待审状态不因更新介绍消失。

这是一项人工/AI 开发约定，没有后台文档同步或自动归档服务。方法选择由任务决定；保护固定证据、保持说明真实及完整重读维护是本工作区保留的要求。
