## 一、建议确立的总目标

**让当前协作 AI 能把值得保留的工作内容提交为有归属、可追溯、可修订的正式记录，并能按对象恢复研究经过、按新问题发现既有经验。**

这里“正式记录”表示通过存储契约成功落盘，不表示内容已被科学验证。

职责分为三部分：

| 参与方 | 应承担的职责 |
|---|---|
| 当前协作 AI 或用户 | 判断内容价值、选择归属与记录类别、撰写正文、解释经验与类比边界、提出整理和修改 |
| 本地程序 | 暴露可调用接口；检查结构、身份、引用、版本和状态变更；可靠保存；计算影响范围；检索、组装和展示 |
| 调用指导与 Skill | 教 AI 何时记录、如何选对象和层级、如何提交、如何读取回执，以及冲突或失败后如何处理 |

AI 不需要知道具体应创建哪些文件。程序不能仅凭文字流畅、任务完成或检索相似，就判定结论成立。每次调用可以只记录一个必要层级；不强迫 AI 每次都生成 L0–L3，更不补造不存在的来源或中间过程。

## 三、统一的是对象访问方式，不是把所有内容塞进一个大对象

### 3.1 三个独立维度

| 维度 | 回答的问题 | 例子 |
|---|---|---|
| 业务对象类型与实例 | 这段工作围绕什么组织？ | `research` 是类型，“某项专题研究”是一个实例 |
| 记忆层级与记录类别 | 这条记录表达什么？ | 原始证据、一次尝试、问题、经验、研究地图 |
| 状态与适用范围 | 事情进行到哪里，内容能用于什么？ | 研究仍 active，某问题 blocked，某结论 accepted 且仅适用于指定条件 |

建议将用户提出的“主类型数据存储对象”称为**业务对象**，统一访问时称为**对象入口**。一个实例可以管理多条记忆记录，也可以引用别的对象；它不必在一个文件中内嵌全部历史。

统一入口应覆盖 core-algorithms、knowledge、projects、research、reports、runs，并考虑已有 data、tools。新增类型应能通过登记类型和适配既有结构接入，不要求修改所有上层功能；但“可扩展”不等于允许任意无契约 JSON 被当作合法对象。

已有类型继续保留自己的意义：Run 的参数和执行产物、Report 的交付清单、核心算法的文档准入不能被一个通用 status 或 content 字段取代。knowledge 中的单篇经验/决策可以成为对象实例；不能把整个 knowledge 文件夹算作一个实例。

**一条记录有一个规范归属，可以被多个对象引用。** 一个 Run 已经表达某次尝试时，研究经过引用该 Run；不再复制出一条等价事件。若一次 Run 产生三个可独立修订的结论，仍可以有三个结论身份。

### 3.2 存储选项比较：目标先确定，物理布局后定稿

| 选项 | 优点 | 需要承担的代价 |
|---|---|---|
| 全工作区数据库存正文，业务目录只留入口 | 集中事务和结构化查询方便；完整离线备份可迁移 | 单个研究导出、人工检查、Git 差异及局部恢复需要专门工具；需处理运行中备份一致性 |
| 每个对象一个大文件，内嵌全部层级与历史 | 小对象容易理解和复制 | 历史增大后写入冲突、局部修订、独立引用和差异检查变复杂 |
| 对象所属文件保存规范记录，统一数据库保存派生索引 | 延续现有项目；便于按对象查看、导出和恢复；索引可重建 | 程序必须负责可靠提交、版本一致性和索引补偿，不能让 AI 自行拼文件 |

**当前建议第三种，作为待讨论的架构方向。** 对 AI 而言仍是一个统一存储接口，对人而言仍能看到所属对象的内容。

迁移目标应明确为：换盘符或换机器后保留稳定 ID、原文、历史、复核和关联；索引丢失可重建。只导出一个对象时，列清包含的记录、引用的外部对象和未随包迁移的材料。外部原件的链接不会因为复制工作区自动可用，需要来源路径映射及缺失报告。

不能只说“复制目录即可完整迁移”，也不能把“数据库可重建”误解成“AI 写过的研究总结可以丢弃”。

## 四、L0–L3：先确定内容职责，再选择格式

按用户澄清，层级确定为 L0–L3，不增设第五层。下面进一步细化各层职责；跨项目能力见 6.3 节。

| 层级 | 建议职责 | 典型内容 | 与其他层的边界 |
|---|---|---|---|
| L0 原始材料与来源 | 回答当时拿到了什么 | 文档、代码/数据版本、实际取得的对话、运行产物及定位 | AI 新写的归纳不能伪装成原始证据；外部原件通常保存引用 |
| L1 过程与结果 | 回答做过什么、观察到什么、为何转向 | 尝试、观察、失败、决策、问题及答案引用 | 保存可核对的经过，不要求复制全部工具输出 |
| L2 有边界的经验 | 回答从这些尝试中可复用什么 | 方法建议、失败条件、适用前提、反例、下一次验证条件 | 可源于一个或多个对象；未复核经验也可作为候选检索 |
| L3 对象/主题研究地图 | 回答现在如何理解这项研究 | 目标演进、路线、关键结果、冲突、未决问题、导航 | 是有依据的阶段综合；不重复粘贴全部历史 |

层级不是可信度等级，也不是每次工作必须走完的流水线。L0 可能有误，L2 经验也可能尚未复核。L2 允许跨研究来源，L3 允许组织跨对象的主题地图；检索、总结或关联分析覆盖多个项目，不改变记录的层级和可信状态。

检查点、检索包和“完整研究经过”建议作为辅助记录或输出，不占一个新的知识层级。一个检查点可以引用所有层级。

### 4.1 格式目标

- L0 不限于 Markdown。应支持原始文件、已登记链接以及来源定位；原始文本导出可以是 Markdown。
- L1–L3 都需要机器可校验的共同属性；问题、经验等再有各自的结构字段，人类阅读正文使用 Markdown。
- 层级放在记录属性中，不要求物理上每层一个总文件或一套数据库。索引效率取决于统一索引，不取决于所有正文是否挤在同一个文件里。
- 正文与结构字段各有明确责任。同一结论不能同时在 JSON、Markdown、数据库中各自维护一份可独立编辑的主正文。
- AI 撰写的独立综合、关联解释和适用边界属于长期内容。分词、向量、排名、反向引用和纯展示视图属于可重建派生数据。

后续方案再确定 JSON 与 Markdown 的具体组合、schema、字段以及修订目录；本节不锁定文件布局。

## 五、属性、子结构与独立对象应如何区分

判断原则：**需要独立引用、独立修改、独立状态或独立历史的内容，应有稳定身份；只解释某条记录的内容，可以作为该记录的子结构。**

### 5.1 属性归属建议

| 所属位置 | 属性职责 | 必须避免的混用 |
|---|---|---|
| 业务对象 | ID、类型、标题、业务生命周期、关联对象、记录策略及权限约束 | 研究 completed 不等于全部问题 resolved；对象不能只有一个代表所有结论的可信状态 |
| 每条记忆记录 | ID、规范归属、层级、类别、标题、作者与时间、保存原因、来源、内容版本、修订原因、发现范围 | 创建人和复核人分开；全工作区可发现不等于向外部公开 |
| 来源/引用子结构 | 目标 ID、固定修订或指纹、定位、关系含义；读取时补充当前可访问性 | 未取得、未知、不适用要可区分；文件不存在不代表相关事实为假 |
| 经验/失败子结构 | 主张、适用条件、禁用条件、失败类别、测试范围、不能推出什么、再试条件 | 一次失败不能升级成普遍不可能 |
| 问题实体 | 问题状态、影响的决策、缺失证据、解决依据、替代问题 | 状态不挂在整个 L1 或整个 Research 上 |
| 结论与复核记录 | 结论范围、复核状态、复核人、时间、依据、所绑定版本、替代结论 | 地图、摘要和检索命中不单独获得一份重复的科学复核 |
| 衍生有效性 | 来源变更、待重验、缺失、索引过期及原因 | 待重验不直接覆写 accepted 历史；应停止当作当前有效的正式依据 |

上述是字段责任范围。正式方案要为每个字段明确必填性、数据类型、默认值、未知值和修改权限；不能只列字段名。

### 5.2 各种状态分别回答什么

| 状态轴 | 取值/含义 | 必须保留的规则 |
|---|---|---|
| 问题状态 | `open / investigating / blocked / resolved / superseded` | resolved 需要答案或明确决策依据；superseded 需要替代问题引用；任务执行完毕不自动解决问题 |
| 结论复核状态 | `not-reviewed / accepted / disputed / retracted / superseded` | 沿用现有证据模型；accepted 绑定依据、范围和版本；撤回保留历史 |
| Run 执行状态 | 沿用现有 planned、running、succeeded、failed 等业务取值 | succeeded 不自动令 claim accepted，也不自动令问题 resolved |
| 关联处理状态 | 候选、采纳、拒绝、撤销等，具体枚举后定 | 采纳导航关联不改变两端结论的复核状态 |
| 保存与索引状态 | 保存是否成功、索引是否追上当前版本 | 保存成功但索引失败应有明确回执和补偿入口 |

同一文档有多条可检验主张时，按 claim 分别复核。文档展示混合状态或“含失效依据”，不能用一个绿色标记覆盖所有内容。既有对象级复核保留兼容语义，但不应借此复制一套新的记忆可信度。

### 5.3 原第三章类型的重新归类

| 类别 | 原计划中的概念 | 建议解释 |
|---|---|---|
| 公共引用子结构 | OwnerRef、SourceRef | 放入需要归属或来源的记录，不各自当作一个记忆层 |
| 记录共同外壳 | MemoryRecord | 所有新增记忆共有的身份、版本和正文承载约定 |
| 有业务内容的记录类型 | ResearchEvent、Experience | 分别表达过程和经验；已有 Run 通过适配直接引用 |
| 可独立演进的辅助实体 | OpenQuestion、Route、Checkpoint、目标版本 | 有自己的状态或历史，按 ID 引用；不必硬塞进某篇经验正文 |
| 有独立语义的关系实体 | Association | 保存两端、关系、依据和边界；跨对象只保存一处规范关系 |
| 检索表示 | Representation | 若含 AI 独立撰写的摘要/边界，要保留规范文本与来源版本；向量和分词可重建 |
| 功能输出 | MemoryPacket、研究经过视图 | 根据当前范围和固定引用生成；需要复现实验或引用时保存快照 |

跨项目经验是一条有内容的新经验或综合记录；“A 与 B 有相似失败模式”是一条关系。这两者不是同一种数据结构，也不因为跨项目就自动更可信。

## 六、需要明确交付的功能目标

### 6.1 AI 提交与修改记录

输入是 AI 已整理好的文本/链接、归属、记录类别和必要依据。程序负责校验、保存并返回记录 ID、版本、实际保存位置和索引状态。

应支持创建、修订、替代和撤回，并能对重复请求给出同一结果、对并发修改报告冲突。内容修改保留旧版本；复核修改保留复核事件；错误结论撤回后不能被旧摘要继续作为有效依据使用。彻底删除属于另外的保留/删除操作，不与撤回混为一谈。

调用入口在底层开发早期就应具备，使开发者可提交合成记录并验证闭环。最终调用手册与 Skill 在已实现契约稳定后编写和演练。

### 6.2 从一个对象恢复研究经过

同一组规范记录应支持两种输出：

| 输出 | 主要读者 | 必须包含什么 |
|---|---|---|
| 人类研究经过 | 用户、接手研究者 | 最初问题、目标变化、尝试与结果、转向依据、关键失败、结论演变、现存争议和待办；每项可展开原记录 |
| AI 续接包 | 当前协作 AI | 当前目标与约束、未决问题、已完成及不应无理由重复的尝试、关键有效/失效依据、下一步及执行前提、需要展开的缺口 |

“完整”表示保存过的关键经过可追溯，不能承诺恢复从未记录的聊天。人类视图可分页、按阶段展开；AI 续接包有预算，并明确省略内容。

确定性的时间线与引用组织由程序生成；需要新的叙事综合时由 AI 撰写、程序保存。程序不应声称仅靠文件拼接就能自动产生优质研究总结。多对象引用组成的输出应能说明采用了哪些版本、哪些材料不可取得。

### 6.3 跨项目索引、跨项目总结与相关性联系分析

按用户要求，以下三项作为独立功能。这里“跨项目”涵盖跨 Research、Run、Knowledge、核心算法等业务对象，不要求记录先挂到某个 Project。

| 功能 | 输入与目标 | 输出及保存责任 |
|---|---|---|
| 跨项目索引与检索 | 在获准范围内统一索引 L0–L3 的可检索内容；根据新问题、当前条件及排除项发现局部成果 | 返回带规范 ID、版本、命中原因、边界和状态的候选；索引是可重建派生数据，不复制一套主正文 |
| 跨项目总结 | AI 根据指定主题或问题，对多个对象的固定版本记录进行比较，说明共性、差异、冲突与缺口 | 临时总结作为功能输出；需要长期保留时，经统一接口保存：可复用经验归入 L2，主题综合与导航归入 L3，并选择一个规范归属、引用各来源 |
| 相关性联系分析 | 程序计算关键词、语义或显式关系等候选，AI/用户解释共同结构及适用限制 | 输出可解释的关联候选；有保留价值的关系通过接口保存为独立关系实体，记录两端版本、依据和处理状态；相似不自动等于支持、因果或已验证 |

跨项目总结中的 AI 新写内容及正式保存的关联解释属于长期记录，不能因为其来源跨项目就只存在于可丢弃缓存。具体字段和保存布局留到技术落地方案确定。

输入不只是问题句子，还包括当前条件、要支持的决策、所属对象以及指定/排除范围。输出应回答：曾经研究过什么相似问题，哪些结果值得参考，哪些方法已失败，哪些条件不匹配，哪些仍缺证据。

必须能发现尚未整理成全局知识的局部结果。默认先返回结果摘要、边界与来源，再按需要展开原文。

候选应区分直接证据、相似问题、类比启发、失败/反证、未决问题；不能把这些混成一个没有解释的相似度列表。相同结果的多个摘要只算一个规范命中，多次转述同一证据不算独立验证。

跨研究关联包含两项功能：程序/AI 提出可解释的关联候选；AI 或用户保存有依据的关系或新的综合经验。相似关系不自动写成 supports。被采用的经验要能关联到新 Run/结果，形成使用反馈，但采用次数不提升复核状态。

后续才确定各检索通道、排序融合、图遍历上限、过滤顺序和评价阈值；本轮不把原计划的 6/14/24 等数字当成既定目标。

### 6.4 价值触发与阶段巩固

触发者是 AI 或用户。程序也可以根据明确事件（如来源指纹改变）列出待检查项，但不独立判断科学价值。

建议的闭环是：**识别实质变化 → 提交本次记录 → 计算受影响对象 → AI 决定是否修订经验/地图/检查点 → 提交修订与理由 → 重检版本、依赖和索引。**

实质变化包括新结果、改变下一步的失败、适用范围收窄、目标变更、冲突以及用户要求保留。阶段结束、切换路线或用户要求时可发起巩固。

程序提供“自上次巩固以来变了什么、影响了哪些条目、哪些仍未处理”。AI 决定如何综合，而不是让程序用调用次数代替价值判断。无变化的重复巩固不新增同义记录；如果用户提出新解释或 AI 修正旧综合，应保存为有理由的内容变化。

巩固不是覆写历史：旧经验可以被修订、质疑或替代，旧尝试和复核依据仍保留。未处理项不能因生成了一篇新地图就被全部标为完成。

### 6.5 工作台

| 用户操作场景 | 应展示和提供的动作 |
|---|---|
| 看一个研究/项目/Run | 概览、关键记录、问题与路线、研究经过、来源和历史版本；按对象能力显示适用内容 |
| 查过去是否研究过 | 输入新问题和当前条件；展示候选类别、命中原因、适用边界和展开证据 |
| 看跨研究联系 | 从命中项进入局部关系，区分归属、支持、反证与类比；查看关系依据 |
| 汇总跨项目经验 | 选择主题和来源范围，导出供 AI 总结的材料包；查看已保存综合的共性、差异、冲突、缺口和固定来源 |
| 处理变化与错误 | 查看内容差异、来源变化、待重验和下游影响；通过统一服务修订、记录复核或处理关联候选 |
| 继续研究 | 生成并复制/导出 AI 续接包；保留当前目标、版本和缺口 |
| 检查是否写入成功 | 分别显示记录保存、索引更新和结论复核状态，并给出可操作的失败信息 |

工作台不只是 L0–L3 文件浏览器，也不要求用户手填全部 JSON。没有额外 AI 会话执行通道时，“生成续接包”只交付续接内容；AI 撰写的新总结通过现有协作会话完成。

## 七、正式开发计划如何做到可以准确开发和验收

目标讨论后，正式计划分成三部分：

1. **技术目标**：功能场景、输入/输出语义、用户可观察行为、边界与非目标。
2. **技术落地方案**：现有实现映射、数据结构及字段、规范存储、关键函数、算法与不变量、错误恢复和迁移。
3. **开发与验证任务**：以具体代码交付物拆分，每项绑定用例、依赖和完成证据；契约稳定后才能确定可并行部分。

每个实现任务采用可单独阅读的任务卡：问题 → 修改位置 → 输入结构 → 输出结构 → 实现步骤/算法 → 失败与恢复 → 测试 → 前置依赖 → 完成证据。不再用一张同时混入产品愿景、代码改动和笼统结果的大表替代计划。

每个测试用例应说明固定前置数据、具体调用、期望返回、落盘变化、不应改变的对象、失败码/恢复结果以及验收断言。下表只示范测试精度，不是尚未确定的函数设计。

| 目标 | 应达到的代码用例精度 |
|---|---|
| 问题不能因任务完成而解决 | 准备 investigating 问题和关联 Run；Run 更新为 succeeded 后问题仍 investigating；无解决依据的 resolved 请求被拒绝且原记录不变；补齐合法依据后才能变更并留下历史 |
| 保存与索引状态可区分 | 提交有效记录时注入索引失败；记录可按 ID 读取，回执明确索引待更新；相同请求重试不产生第二条记录；补偿后可被检索 |
| 动态进度不误伤复核 | 准备已接受结论及固定依据；只新增检查点后原复核仍可按原范围使用；修改被引用证据后正式检索拒用并列出影响路径 |
| 一个对象可恢复经过 | 合成两条路线、一次失败、一次目标变更和一个未决问题；输出保留转向依据和旧目标引用，显示未决问题；来源缺失时明示缺口 |
| 撤回不被过期摘要绕过 | 建立经验、摘要、地图和报告的已登记依赖；撤回来源后，即使索引仍旧，正式使用检查也拒用受影响结论；历史视图保留原文和撤回事由 |
| 跨项目索引不复制规范记录 | 准备两个研究引用的同一经验及一个排除对象；跨项目查询只返回一个规范经验命中且不返回排除对象；重建索引前后规范 ID、原文和修订保持一致 |
| 跨项目总结沿用四层 | 准备两个对象的固定版本结果；提交 AI 撰写的经验或主题地图后，分别保存为 L2 或 L3，并保留单一归属和全部来源版本；请求不存在的层级时拒绝且不写入 |
| 相关性与证据支持分开 | 准备两个相似但未建立支持关系的对象；生成并采纳导航关联后，只新增规范关联及处理历史，不增加 supports 关系、不改变两端复核状态；来源版本变化时显示关联需重检 |

另行测试 AI 调用质量：让 AI 根据固定材料选择记录方式、提交、检查回执、处理冲突，再由另一轮 AI 只凭保存记录续接。测试程序能确定性验证身份、字段、引用和状态；经验是否准确概括、类比是否合理，需要有标注依据的评价，不能靠 schema 通过证明。

最终调用指导与 Skill 应解释对象和各层含义、选择规则、最小有效输入、何时引用已有 Run、修改/撤回流程、成功回执和失败处理，并绑定真实可调用接口。在这些接口与核心算法完成后进行完整演练，不能提前用一份提示词代替底层实现。

正式代码阶段遵守现有 Windows x64 升级约定，明确新业务记忆的保护范围、索引重建、外部来源映射和恢复；涉及安装/扫描/清单等变更时执行真实 setup 扩展旧工作区测试。合成数据通过与第二台物理机、真实业务效果分别报告。

## 八、已确认事项与后续讨论

已确认：仅保留 L0–L3；跨项目索引、跨项目总结、相关性联系分析为独立功能。原稿中待定的第五层建议由本次用户澄清取代。

后续讨论继续围绕以下建议，不再讨论增加层级：

- 统一业务对象入口，保留现有类型专用结构；记录有一个归属、允许跨对象引用。
- 对象所属文件保存规范内容、统一数据库保存派生索引，作为后续架构论证方向。
- 研究经过分别提供人类阅读视图与 AI 有界续接包；AI 新写综合作为长期记录保存。
- AI/人触发内容整理，程序负责可靠保存和影响计算；工作台覆盖查看、检索、纠错与续接。

本轮没有实现上述新接口，没有创建或安装新 Skill，也没有运行新功能测试。除明确列出的用户确认外，其余内容仍为讨论建议。
