# 按影响选择验证

本页规定测试强度，不规定固定开发流程。根据功能重要性、改动大小、影响范围及失败后果选择有用的检查；选择理由写入本次计划/摘要即可。复杂执行可用现有测试器保存冻结选择与独立回执，命令和 AI 场景见 [TESTING_REFERENCE](TESTING_REFERENCE.md)。

## 选择范围

| 改动 | 验证目标 | 通常采用 |
|---|---|---|
| 纯文档、计划、低风险规则调整 | 现行含义、链接、入口和历史保护 | 定向文档核对；不强制创建新 Run、跑 quick/full 或生成 AI 验收全套记录 |
| 局部低风险功能或明确缺陷 | 改后行为可用、关键失败边界不回退 | 轻量核心：受影响行为的现有测试，必要时补真实故障用例；不为可逆改动编写只匹配实现文字的测试 |
| 重要功能、跨模块或状态/契约变化 | 主要使用链路、调用方、失败/兼容边界一致 | 详细关键功能回归，覆盖架构影响表的相关路径；可用 quick 加影响能力，但不是默认要求全库回归 |
| 全局重构、广泛影响的收口或发布 | 受影响系统整体可交付 | full 及相关集成/交付检查，明确依赖缺失和未执行项 |
| AI 调用、语义内容、研究续接方式变化 | AI 实际能完成本次任务 | 在软件检查之外选择相关 A01–A09；不自动全选，普通界面/文案改动不默认触发 |

通过必要检查后，只有新改动、失败或未解决风险才扩大/重复验证。复用已有证据先核对版本、输入和适用范围。新增能力/真实故障补入可复用测试目录；已选测试不能为追求通过而降低标准。

当前 `testing prepare --tier quick` 的选择器仍包含固定跨栈门槛和影响能力集合，**不等于上表的最小轻量集合**。轻量检查可直接运行相关既有测试并记录结果；本规范不虚构尚未实现的“轻量 tier”。需要机器冻结、全量核对或完整执行时再用 quick/full 工具，详见执行参考。

## 测试点生成与持续维护

从本次目标和架构影响路径识别用户可观察行为、状态转换、关键失败/拒绝及兼容边界，再选择已有测试；确有缺口时补行为用例。真实故障尽可能固化原触发条件与错误结果，修复后验证正确行为；不要只匹配实现文本或为增加数量重复测试。测试点由开发者/AI 设计，静态发现只能发现已有用例，不能证明需求没有遗漏。

测试定义和基线成员唯一维护在 `automation/testing/catalog.json`；具体断言在该项 `path` 指向的测试中，执行证据留在任务摘要/Run。新增、改名、移动或删除用例时同步登记并盘点；功能、契约、来源边界变化及真实故障出现时，检查相关测试的断言和负例是否仍有效。修改相关能力时同时复审它的基线，发布前通看基线覆盖缺口；不要求每次小改动复审全库。

## 基线防线的准入、复审与退出

基线是 `quick=true` 的固定跨栈防线，用于保护重要且需要长期保持的行为，不是全部功能测试，也不是每次开发必须全跑的集合。新增登记默认只进入 full；选择 quick 时，工具合并固定基线、受影响能力和显式追加项。轻量任务仍按上表选相关检查。

- **准入**：用例保护数据/权限/固定版本/恢复等重要边界，或核心用户链路、跨层契约、后果严重的真实回归；具有明确断言、可重复输入和可解释成本。先找现有覆盖，避免重复堆入；较慢但不可替代的交付防线可以保留，并说明原因。新增重要能力必须作出“加入基线 / 已有覆盖 / 仅按影响执行及理由”的明确判断，不因已登记就视为已覆盖。
- **逐项依据**：基线项的 `baseline` 对象维护 `risk`（失效后果）、`reason`（保留理由）、`review_triggers`（相关行为/边界变化）、`reviewed_at`、`reviewed_by` 和 `review_basis`。复审记录是设计判断，不代替执行结果；未知的历史选入日期或原始理由不补造。
- **复审**：触发相关变化时检查是否仍能捕获目标故障、断言是否变弱、是否与其他项重复、依赖/成本是否适合固定执行。记录保留、加强、替换或退出及原因；同时检查新能力有没有基线缺口。没有触发无需机械改日期。
- **替换/退出**：只有原行为已正式取消、风险已消失，或已有明确替代测试覆盖相同必要边界时才能退出。替代须记录具体测试 ID、覆盖对照和实际验证依据；保留原项时把 `quick` 改为 false 并保留其依据，删除用例时在清单历史保存旧项。慢、环境缺失、暂时失败或追求通过率均不是退出依据；暂未运行如实记录 incomplete/未执行。
- **变更留痕**：同次变更更新清单 revision，在 history 记录操作者、时间、原因、受影响 ID、前后依据及可用验证引用，并保留旧清单/差异。已冻结选择不回写；需要执行新范围时生成新选择版本。新增或替换的防线需实际验证，纯补充依据可定向核对清单与选择行为。

这些字段是开发维护约定；当前 `audit` 不强制校验 `baseline` 字段或判断风险覆盖，也没有自动晋升/退出命令。修改清单后人工/AI 核对依据完整性，再用 `testing audit` 检查登记与定位。当前基线的依据补录不等于对新材料查询等所有能力完成了全面覆盖审查。

## 不能省略的风险检查

- 校验、目录扫描、缓存边界、工具登记、框架清单、安装或恢复逻辑变化：真实 `setup.cmd` 扩展旧工作区场景，覆盖预览、升级、重复升级、恢复、完整受保护文件/目录及真实损坏拒绝。见 [UPGRADE_TESTING](UPGRADE_TESTING.md)。
- 前端变化：相关组件、实际浏览器、类型检查、构建和资源指纹；使用端不依赖 Node。详细命令见 [WORKBENCH_DEVELOPMENT](WORKBENCH_DEVELOPMENT.md)。
- 依赖/模型变化：真实离线安装、升级、接收端再次打包与恢复，不能用 core 安装替代。未变化的依赖不必重复打包。
- 检索、表示或知识语义变化：范围/排除、固定引用、正式准入、L0 边界、预算及相关性；涉及策略收益时比较准确度、召回、错误关联、延迟和上下文成本。
- 每次代码修改核对 Windows x64 与旧工作数据升级边界。第二台物理机及真实业务验收独立；当前万条规模测试保持暂缓。

## 结果怎样记录

软件执行、实际 AI 自查、人工反馈与科学复核分别保存，不能累加成一个通过率。失败、跳过、未执行及待审如实保留；`audit/coverage` 是盘点，代码阅读是静态核对，都不等于行为测试通过。

实际 AI 需真实读取、生成请求、走公开入口并固定回读，然后自行评估；程序不能代填。A02 必须是真正独立上下文，人工没有给结果仍是待审。人工页只包含本次新增及重要受影响功能。

小任务在计划/摘要记录目标、影响、检查及结果；有独立输入/输出或长期复用价值的验证用 Run 固定源码、输入、命令、回执与限制。已有失败和旧版本保留。结构变更执行 `refresh-index`、`validate`；本页不要求每次都创建全套分层成果。
