# AI 辅助研发工作区调研底稿

- 日期：2026-09-04
- 受众：工作区设计者与研发工程师
- 范围：AI 上下文工程、代理工作流、研究数据、可复现分析、血缘、知识与报告自动化
- 地域：工具中立；企业制度以用户所在公司为准
- 排除：不对公司合规状态、共享盘能力或具体商业平台作未经验证的假设

## 执行摘要

证据支持建立“小型控制平面 + 外部数据平面”。根 `AGENTS.md` 作为路由，正式知识版本化，任务上下文渐进加载；数据与代码物理分离、逻辑关联；分析以 Run 为最小证据单元；模型、数据与验证双向链接；复杂任务用可恢复计划；重要选择进入 ADR，显著失败进入无责复盘；报告引用固定 Run；安全依赖最小权限、审计和人工批准，而不是自然语言自律。

## 关键结论

1. 根指令应短小并分层，避免巨型说明占满上下文。
2. 文档、代码、schema、计划和验证产物共同构成仓库内事实系统。
3. 原始大数据留在受控存储，工作区登记数据引用、契约、版本/指纹和血缘。
4. 每次分析/仿真生成唯一 Run，绑定输入、代码、参数、环境、指标、产物与状态。
5. 核心算法卡同时覆盖接口、算法、Verification、Validation、UQ、适用域和数据依赖。
6. 自动记忆只能进入候选区，审核/验证后才可晋升为正式知识。
7. 研究与诊断采用“问题—假设—证据—反证—验证—综合—写回”闭环。
8. 报告是批准 Run 的可执行视图，而不是新的孤立真相源。
9. 外部内容一律视为不可信数据；外发与写操作需要硬权限和审批。

## 局限

- 公开资料不能确定公司的数据分类、合同、部署区域、允许工具和设备控制政策。
- 多数 AI agent 工程报告时间较新，长期维护效果仍需本地度量。
- 具体工作流编排、实验跟踪和数据版本平台应在首批真实案例后选型。

## 建议

以文件化 schema 和 Python 标准库工具启动，用三个真实案例验证：一个核心算法算法、一个大数据诊断、一个研究到 PPT 的闭环。收集检索时间、复现实验时间、重复脚本比例、报告手工改数次数和复盘复发率，再决定平台升级。

完整来源与声明映射见同目录 `claim-source-ledger.md`。
