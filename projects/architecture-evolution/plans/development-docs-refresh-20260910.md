## 依据与取舍

对照原 development-checks 与 [GPT-6 Astra 官方建议](https://developers.openai.com/api/docs/guides/latest-model)：官方强调审查 Skill/规则中的冲突，按任务校准验证范围，必要检查通过后不无故扩大或重复。它没有要求取消所有流程；本轮据用户意图保留项目约束，去掉固定工具顺序。

| 原约束或缺口 | 本轮处理 |
|---|---|
| 每轮固定 audit → prepare → validate → run → 登记回执 | 改为按重要性/大小选择验证；轻量任务可直接记录于计划/摘要，工具命令放按需参考 |
| quick 被当作日常最小检查，但选择器实际包含跨栈固定门槛 | 明确工具现状；轻量可定向执行已有测试，没有虚构新 tier 或修改选择器 |
| 必须知道架构，但现行总览缺少 MQ 独立职责 | 重写 ARCHITECTURE，补材料查询应用、依赖、状态权威和实际限制 |
| 核心功能解释散在 v0.1 冻结稿和 v0.2 历史设计 | 新建稳定 docs/CORE，解释实际输入输出与衔接；精确字段仍由运行代码负责 |
| Project 图与公共架构各维护一份 | 全局影响表归根 ARCHITECTURE；旧 Project 文件只作导航，原记录不改写 |
| docs 的历史与现行入口混杂 | 新建分类索引，旧设计/基线/fixture 原地保留；后续计划和执行记录回所属 Project/Run |
| 开发后泛泛要求“更新 README” | 明确六份短文档需完整重读、逐项维护，细节按影响同步 |
| 每次规范整理可能被要求补齐分层成果 | 明确文档/规范/排期可记计划/摘要，不虚构技术经验或双文稿 |
