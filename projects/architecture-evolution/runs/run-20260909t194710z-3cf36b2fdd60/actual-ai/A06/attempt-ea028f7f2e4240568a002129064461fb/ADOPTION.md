## 可以有条件参考的内容

可以在 API 策略分析中采用“先检查适用前提，再按动作是否触顶分段检查”的方法。水箱模型把未饱和线性段和泵触顶后的动力学分开；对应到 API，只能用这一分析次序检查等待尚未封顶与已经封顶两种情况，并分别检查成功、可重试失败、不可重试失败以及次数终止。

API 材料给出

\[
d_k=\min(d_{\max},b r^k),\qquad b=0.2\,\mathrm s,\quad r=2,\quad d_{\max}=3.2\,\mathrm s.
\]

其中，\(k\) 是连续失败后的重试序号，\(d_k\) 是下一次等待时间；\(b\) 为初始等待，\(r\) 为无量纲倍率，\(d_{\max}\) 为等待上限。采用此检查方法前，必须明确幂等或去重语义、错误分类、请求超时、最大总耗时，以及文中“总重试上限”的计数约定。给定上限本身并不包含这些保证。

待执行的验证可使用成功、连续失败、不可重试失败、接近等待封顶、达到次数上限、多客户端同步重试的独立事件序列，检查终止、耗时和重复副作用。这些验证本次尚未执行，不能称为算法性能已改善。

## 不能推广的内容

不能把水箱比例增益 \(K\) 与 API 倍率 \(r\) 互换，也不能从水箱的误差衰减推出 API 稳定、最优吞吐或最终成功。水箱有状态方程与流量守恒，\(K\) 的单位为 \(\mathrm{m^2/s}\)；API 只有离散失败序号和等待策略，没有服务端队列、容量、到达率或响应概率模型。

本次检索得到的水箱 r2 进一步说明目标所需流量超过泵上限时，仅增大增益不能使目标可达。这个结论仅属于给定水箱参数；它提醒检查限制条件，但不能转写为 API 成功概率的定理。若要评价 API 稳定或成功率，仍须补充服务端与负载模型、响应延迟和并发策略，再做独立验证。
