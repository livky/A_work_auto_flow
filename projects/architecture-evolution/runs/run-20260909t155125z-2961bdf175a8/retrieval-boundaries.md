## 用 RepresentationSpec 讨论抽象程度

这里的 RepresentationSpec 是候选概念名，用于描述“针对同一内容选择哪种表示”，不是本轮已经添加的 JSON 字段。它不能直接等同于现有的 L0–L4：当前层级描述来源、技术单元、事件/决策、经验和地图，跨层不保证内容量严格递减，也不保证形成完整的逐层压缩链。

| 候选表示 | 含义与适合用途 | 与现有代码的关系及限制 |
|---|---|---|
| `original` | 按固定来源直接读取原始材料，用于追溯和核验 | 对应 L0/文件 Ref 的显式读取能力；保留授权与版本检查。选择该表示不自动开放全库原始日志搜索 |
| `full` | 某个内容对象的完整规范正文 | 可复用技术单元完整块、文稿及普通记录读取；“完整”必须说明对象边界，不等于所有底层原件 |
| `section` | 指定文稿章节或有稳定定位的内容片段 | 复用独立章节/技术块；属于粒度选择，必要定义闭包可能额外增加内容，不能保证总比全文小 |
| `unit_digest` | 单技术单元的短描述，保留问题、方法、发现、适用/不适用与限制 | v3 `retrieval_description` 已提供接近的能力；搜索命中短描述后可按固定 Ref 下钻完整技术块 |
| `topic_synthesis` | 围绕明确问题/专题综合多个技术单元 | 可以引用已有研究综合或文稿，尚无通用“自动专题层”契约；要固定覆盖来源、遗漏、冲突和生成依据 |
| `domain_synthesis` | 更大领域内的知识组织与综合，用于先定位专题和边界 | 是可扩展的目标能力，不是当前 L4 的另一个名字；不能假定总有比专题更短、更可靠的现成摘要 |
| `lexical_card` | 关键词、别名、术语和触发条件组成的检索卡 | 偏向匹配表示，不是面向人的科学摘要；可借用 keywords 和 representation，但不能替代完整依据 |
| `relation_graph` | 带类型、方向、来源和版本的关系视图 | 结构化导航，不在“文字由长到短”的全序中；局部图遍历成本取决于边数和范围 |
| `process` | 研究过程视图，保留路线、分支、未解问题和验证过程 | 当前独立 `research_process` 文稿；是阅读目的/编排维度，可以自身有 outline、section 或 full |
| `report` | 面向交付的研究报告视图，组织结果及必要依据 | 当前独立 `research_report` 文稿；不保证内容只是过程稿的机械压缩，也不能用短报告替代缺失过程 |

宜将概念拆成几个正交维度：表示种类、内容粒度、阅读视图、匹配字段和返回模式。例如“检索 topic_synthesis，返回 unit_digest，再按选择读取 section/full”，或“在 process 视图中只读一个章节”。公开能力应能列出实际支持的表示及其来源版本；为未来表示保留受控扩展标识，遇到未知或尚未生成的表示明确返回 unsupported/missing，并由请求决定是否回退。现在不必实现任意表示插件系统。

RepresentationSpec 还应表达保存的既有表示还是允许现场生成、覆盖哪些固定来源、是否允许摘要过期回退，以及该表示的生成/投影版本。表示层的“新鲜”来自依赖版本相符，正式可信度仍来自结论与复核政策。专题/领域综合即使按授权策略成为正式知识，也需要保留来源与适用限制。

上层材料预先生成且数量较少时，确实可能降低扫描和上下文装载成本；这是需要基准验证的性能假设。现场生成综合、补查冲突、展开密集关系图或回源检查可能增加耗时。抽象程度和耗时预算应独立选择；不要把“高层”作为“更快”“更可信”的无条件保证。

当前 schema 的 `RepresentationPayload.slot` 只有 title/result/problem/trigger/failure/boundary（`automation/schemas/memory-v3.schema.json:1413`），它描述目标内容的检索切面，不是上述抽象层。正式实现前需决定新增表示是在检索请求/投影目录中表达，还是哪些综合本身是新的规范内容对象；不能仅给现有 slot 改名称就宣称支持全部表示。

## 表示、排序与材料包如何分工

1. **规范内容层**保存原始事实、完整技术块、作者提供的关键词/检索描述以及固定来源。不知道下游使用哪种向量模型，也不依赖某个排名公式。
2. **检索投影层**选择此次可索引的文字，标识完整正文、技术描述或翻译/改写等表示；记录投影版本与源版本。模型变更通常只重建向量投影；内容语义变更才需要审视表示规则。
3. **召回和排序层**用查询范围选择候选，按规范 ID 归并与排序。候选包含为什么命中、命中哪种表示和固定读取入口，不要求此时把全文交付给 AI。
4. **上下文层**按任务角色和内容模式展开候选，补齐变量定义等依赖，控制最终上下文体积，保留必要限制、来源与遗漏。自动综合与整理可以按用户授权策略修订正式知识，但应经独立的内容维护/写入流程，保留版本、生成依据、复核与恢复入口；排序器不临时改写命中正文。

当前实现特别需要注意：v3 detail 的 `memory/index.py:254` 将完整块排除出检索投影，body 实际是保存的 `retrieval_description`；keywords 在 `:351` 合并进 text。FTS 的 `title/text` 并不代表“完整技术正文全文检索”。搜索的 `snippet` 是当前投影前 400 字符（`memory/search.py:644`），完整适用边界另外返回。`packets.summary_projection` 明确是确定性短投影，不调用生成模型。

## 关联不等于科学支持

关联是“继续看哪份材料”的理由，科学支持是“该结论在给定适用域是否有合格依据”的判断。`memory/associations.py:191` 拒绝把 supports/input 写成导航关联；`:232` 的邻居扩展只用 accepted、未过期且非科学支持的边。相似模型或关键词共同出现只能产生候选，不改变 claim 复核状态。

生产默认 `memory context` 只调用 search 后展开固定引用；完整图方案见 `memory/evaluation.py:174`，它另行读取关系、回查端点、展开邻居并组包。设计上可以为图候选预留统一入口，但不能把评估方案当成当前默认行为。当前 semantic association 仍在 `memory/associations.py:164` 读取 `body_markdown`；对 v3 完整技术块的表示应由第 4 组统一定义后再评估。

## 状态、预算与渐进替换

建议保留四种独立状态：规范内容提交是否成功；各投影是否追上目标版本；本次查询/材料包是否完整及如何降级；结论或关联的领域状态。它们各有权威来源，不压成一个 success。当前 immutable commit 中已有 index_pending（`memory/store.py:301`），索引状态有各通道代次，包有 basis_heads 和 omitted，足以作为渐进演进起点；不必立即引入队列或事件总线。

后续可以按三个小步骤验证职责划分：

1. 先约定查询范围、固定候选、交付内容和执行回执的最小共同语义，并为两条旧路径做兼容适配。未支持的时间/字段/截止要求明确报告；保留各自业务行为和历史 ID。
2. 提取只读内容与证据端口、纯排序及表示构建，解除私有方法和数据库类型泄漏；在同一进程中使用构造注入即可，不需要动态插件发现。
3. 使用固定问题与反例检查语义等价，再分别试验候选过滤下推、有界向量窗口、按需补偿索引或可选图候选。记录召回质量、实际交付质量、误关联、延迟、索引追赶成本；不能只看返回条数或接口测试通过。

预算应分别命名和计量：最终候选数、各通道候选计算量、图跳数/节点数、上下文 Unicode 码点或指定 tokenizer 的 token 数、运行耗时。当前只有部分数量/码点上限及总耗时观察，没有硬延迟保证；统一设计要明确超时后的部分结果、未执行通道和重试依据。

## 暂不抽象的内容

- 不建立能表达任意 SQL/图查询的通用 DSL；先满足已经讨论清楚的 owner、时间、内容类型、状态和内容模式需求。
- 不为 v1/v2/v3 的每个字段建立一层仓储接口；稳定的是版本读取、固定引用和提交语义，字段兼容仍由明确 schema/适配器处理。
- 不把 RRF 常数、BM25 权重、CJK 分词、具体模型窗口、Qdrant 分批大小、SQLite 表名当成领域公共接口；策略版本和能力回执足够暴露必要差异。
- 不合并相似关系、引用关系、科学支持关系和代码调用关系；共享“有两端”不足以证明它们因同一原因变化。
- 不立刻引入微服务、消息队列、全局缓存、任意插件加载器或第二份事实数据库；当前可先通过少量端口和同进程组合验证收益。
- 不让排序或召回隐式承担正式知识修订。按用户已允许的自动整理策略，可自动生成并提交正式知识的新修订；使用规范写入接口保留 actor、策略版本、变更原因、固定依据、expected_head 与恢复入口，并依据内容变化重算复核有效性。保存成功不能继承不适用于新内容的旧确认，也不要求所有整理永远停留在候选状态。
